## 7. Narrow trusted writer and proposed database interfaces

### 7.1 Two distinct authority domains

Server actions authenticate with the existing trusted session, resolve the current Business, check the appointment and allowed command, and obtain the server-only service client. They pass the **server-derived** actor and Business; browser IDs are selectors to revalidate, never authority. Every RPC independently checks current Business owner/admin membership and every relationship.

Original create/bind/payment/recovery retain original-actor equality. Operational maintenance may be performed by a different currently authorized O actor. Record both original creator and actual editor; never impersonate the original actor to satisfy v1 checks. A noncreator cannot acquire original tender details or resume/collect the creator's unresolved payment by invoking maintenance. Cancellation/customer correction may fence that attempt through explicit team-authorized lifecycle authority, with no payment execution.

Proposed functions remain SECURITY INVOKER, pinned `pg_catalog, pg_temp`, fully qualified relations, literal service-role entry check; EXECUTE only to service_role, revoked from PUBLIC/anon/authenticated. Existing server identity discipline is retained. No new browser table privileges, role memberships, RLS broadening or FORCE-RLS change. A `channel`, client boolean, user metadata, or transaction setting is never a bypass credential.

Money state comes from existing authorized canonical readers, not a second sum in the action.

### 7.3 Guard and audit mechanism

Propose one private append-only lifecycle command journal and one `appointments.operational_revision` counter (initial 0). Use a private/non-API schema with explicit access controls and RLS defense in depth; no browser access or sequence privileges. No new role is needed. Journal rows have same-Business composite references, unique `(business_id, appointment_id, mutation_id)` and unique applied-effect revision (no-op records do not consume a revision), retain the canonical bounded command tuple (not only its hash), actor, operation, expected/result revision, transaction identity, reason and exact whitelisted pre/post images. Notes are sensitive tenant operational data: restrict access and bound retention with retained appointment history; do not copy contact details or full arbitrary payloads.

RPC acquires K, rechecks authority and state, and checks prior mutation identity **before** expected-revision rejection. Same ID/same tuple returns original effect evidence plus current state; same ID/different tuple rejects. An old successful command replay never reapplies its old after-image over a newer revision. A no-op has a replayable result and no extra revision/notification.

**C10 adopted: the private journal row itself is the permit.** No separate permit table, mutable consumed flag or additional credential system. An applied row is append-only evidence and an authorization for precisely one transition from revision R to R+1 within its creating transaction. An applied-effect uniqueness rule covers `(Business, appointment, result_revision)`; mutation identity is separately unique. NO_CHANGE rows carry a replayable result but no applied-effect revision, grant no write authority, and produce no extra event or revision on replay.

The parent guard must explicitly match **transaction identity, Business, appointment, operation, mutation identity, actor, command, expected revision, actual OLD pre-image, expected NEW post-image and exact allowed field set**. Compare journal pre-image to OLD and post-image to NEW (including revision); verify all unlisted fields are unchanged. It is not enough to compare supplied hashes or a proposed before-image with another supplied value. Guard-side actor/tenant/terminal/financial checks still apply. A caller-supplied GUC is not authority.

One accepted command proceeds: acquire K; validate current row and complete desired resources; append journal permit; apply each enumerated child delta once; perform the single final parent mutation R→R+1; assert exact parent/child after-state before return. Pure resource maintenance still advances the parent revision once. Any failure rolls back journal and all effects. The monotonic parent revision consumes the permit: it cannot match OLD a second time, cannot be reset by this or another command, and cannot reuse the unique effect revision. Different permitted commands within one transaction require different mutation IDs and successive revisions. A no-op never uses this write permit flow.

For child maintenance, the journal also fixes sorted before/desired resource sets and finite row deltas. Delete only before-minus-desired rows; insert only desired-minus-before rows; untouched intersections cannot be churned. No linked child row UPDATE is needed by the proposed writer: reject it and implement membership changes as explicit authorized delete/insert. This still guards UPDATE attempts, including attempts to move a row to another parent. Unique child membership plus disjoint deltas prevents replay of an inserted/deleted row; parent revision must still equal R during child work, and final R+1 closes further child authorization. Whole-set verification belongs to the RPC, not this row guard.

The service role remains a trusted server principal with existing privileged capabilities. This is not a promise against compromise of that principal. Browser/authenticated callers cannot create journal permits or execute W. Direct service-role guarded writes without exact permits are refused. Transaction identity alone authorizes neither a second update nor unrelated fields/rows. Retain existing best-effort operational logging only if it cannot duplicate the canonical journal effect; it is not the atomic audit authority.

### 7.4 Parent DELETE and child resources (C1, C4, C6)

Future parent guard covers INSERT, guarded UPDATE **and DELETE**. For DELETE, inspect OLD: return OLD early only for unlinked legacy rows; reject every non-null operation-linked row, including service-role/admin and cascaded deletion. No maintenance journal can authorize linked DELETE. Preserve original INSERT and legacy NULL/NULL UPDATE behavior. Failure aborts the deleting statement/transaction and preserves related resources, invoices, ledger and attempt relationships; no child cascade is an alternate cancellation or cleanup path. TRUNCATE/disabled-trigger administrative capabilities are not granted by this design and are outside this row-trigger guarantee.

`appointment_resources` has no `business_id`: resolve Business and linkage from the parent appointment. INSERT uses NEW parent, DELETE uses OLD parent; UPDATE must inspect both, returning early only if both are confirmed unlinked. Missing/ambiguous parent on ordinary child DML fails closed; never interpret an RLS-hidden or failed lookup as unlinked, and never let a parent-changing UPDATE escape by checking only one side. No Business-column backfill. For a linked parent require the trusted service writer and validate the individual resource tenant/eligibility and exact allowed event/delta. Cover INSERT, UPDATE and DELETE; linked UPDATE is explicitly refused as above. Unlinked-only behavior remains unchanged.

Legacy unlinked parent deletion legitimately invokes the existing child ON DELETE CASCADE after the parent is gone. Preserve that path using the **paired parent-DELETE prohibition plus validated/enabled FK invariant**, not a blanket missing-parent allowance: only physical parent absence during referential cleanup can qualify, with complete visibility and no disabled/bypassed guard assumption. RLS invisibility, ordinary INSERT/UPDATE, lookup failure or a missing parent outside verified referential cleanup cannot qualify. D1 must freeze and prove that distinction under the actual RI trigger execution principal and ensure legacy cascades still succeed; trigger depth alone is not authorization. No new delete feature, Business backfill or cleanup permit is proposed. If this distinction cannot be proved with the paired guards, stop D1 for a focused guard correction rather than quietly breaking legacy deletion or allowing linked cascades.

For original creation, allow each initial child INSERT only for the exact original linked parent, literal service role, OPEN original operation and a resource contained in its admitted resource set. OPEN alone is insufficient; it does not authorize unrelated resources, UPDATE or DELETE. This row guard cannot prove all desired rows have been inserted. The existing `persist_booking_operation_appointment_v1` already validates resources and inserts the full supplied admitted set transactionally; it **likely needs no body change**. D1 must verify that assumption against the new guard and absence of silent child skips before freezing SQL. Do not authorize a speculative persistence-body rewrite here.

The maintenance RPC validates the complete distinct desired set, applies the finite deltas, and asserts exact-set equality (including empty set and absence of extras) before committing. No BEFORE ROW trigger owns whole-set equality. PostgreSQL transition tables are available to qualifying AFTER, non-constraint triggers on plain tables, not a BEFORE ROW trigger; UPDATE transition tables exclude a column list and transition relations cannot be combined with multiple trigger events. Even a transition table represents a statement's changed rows, not necessarily the complete final membership across several statements. No transition-table machinery is needed for this design's RPC final assertion. [PostgreSQL 17 CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html).

Child guard operation/resource/journal authorization reads are **non-locking**. A linked maintenance child trigger may acquire/reuse only a parent FOR NO KEY UPDATE lock, compatible with the invoking RPC's existing non-key lock (or its stronger lock where already held). It must not upgrade ordinary maintenance to FOR UPDATE, take an advisory operation lock, or later acquire any operation/attempt row lock. Creation reuses its own newly inserted parent; its operation is already serialized by the persistence RPC. Direct unauthorized calls cannot make the trigger enter a reverse appointment→attempt/operation wait. Parent reparenting is rejected rather than locking two linked parents in an invented order. The complete trigger graph and parent disappearance/cascade handling require new proof; resource availability remains a soft check, not an interval lock.

### 7.5 Fresh customer authority and cancellation reason (C2, C7)

On every actual customer change, **inside the appointment guard**, with OLD/NEW and the locked parent, repeat a fresh zero-history check. Inspect all ledger rows linked by appointment ID without business/status/kind/success/date filters that could hide a contradictory or foreign row; also check appointment-linked refund witnesses and refunds linked through those transactions. Refunds, failed-labelled rows, reversals and later independent payments never count as absence. Any history blocks; incomplete/contradictory evidence fails closed without exposing foreign details. The RPC performs its earlier check too, but neither that check nor `close_reason`/`replacement_customer_id` substitutes for the actual guard check. Preserve the composite financial attribution FK as an additional race/integrity barrier.

Customer-change permission is the fresh transaction/revision-bound single-effect journal entry matching expected current customer to the exact replacement. Stale CLOSED metadata is not a reusable credential. **close_reason and replacement_customer_id are not made immutable after CLOSED**: legitimate repeated no-ledger corrections may advance them only through a new validated close command, new mutation/revision, fresh guard check and audit. The operation remains CLOSED; original request/customer/attempt and terminal financial history never change. Preserve first closed_at. Replaying an old correction cannot apply its former target or advance metadata after a newer correction. Future shared-close implementation must bind metadata updates to that command; direct metadata editing alone never authorizes appointment mutation.

Cancellation of an existing appointment requires the exact fresh CANCEL permit and **APPOINTMENT_CANCELLED** close reason. Remove OPERATOR_ABANDONED from the future appointment cancellation guard's accepted reasons: current close_v1 rejects abandonment if an appointment exists and validates cancel=true only for APPOINTMENT_CANCELLED. Abandonment/pricing/slot reasons remain existing no-appointment close/fence outcomes, not extra authorization to cancel an existing row. Existing terminal zero-ledger and recorded-money close semantics remain intact.

Existing `close_booking_operation_v1` needs a narrowly replaced body in the **new migration**, preserving its signature, original-actor check, terminal results and accepted fencing algorithm, while participating in the same journal/revision discipline. Share an internal fenced-close implementation with v2; internal EXECUTE is private/server-only, never a public generic mutation primitive. The v1 adapter's expected-current customer condition remains required; its legacy call has no optimistic revision argument and therefore reads current state under K rather than claiming modern stale-edit protection. Existing pricing/slot/abandon close without an appointment creates no appointment mutation record. v2 changes maintenance actor authorization, not the financial commit actor rule.

No original bootstrap, persistence, bind or money-commit algorithm is redesigned. Reader transport may expose operational revision/current status separately from original request. Old replay must never require current scheduling fields to equal the initial request after a valid edit; original bootstrap request identity still must match exactly.

### 7.6 Current error behavior and future operator mapping (C9)

Current `updateBooking`, `cancelBooking`, `rescheduleBooking` and `resizeBooking` can return raw database `error.message`; a failed RLS lookup may instead report not found. Where a linked UPDATE reaches the guard, the ordinary session/RLS caller generally encounters `BOOKING_OPERATION_SERVICE_ROLE_REQUIRED` first; a service-role caller can reach deeper canonical-close, immutable-field or transition restrictions. Do not claim today's UI already safely maps all of these. Preserve the existing friendly financial-attribution error in `update.ts`.

Future linked routing selects W/X before attempting legacy DML, and normalizes every failure at the server boundary: NOT_AUTHORIZED (no existence/foreign detail), STALE_REVISION (refresh), CONFLICT (slot/assignment unavailable), FINANCIAL_REVIEW_REQUIRED (history blocks this correction), TERMINAL (cancelled/retained row), PAYMENT_RECOVERY_REQUIRED (coherent unresolved same attempt), UNKNOWN (transport or evidence cannot certify outcome). Only verified canonical evidence permits the recovery-required classification; raw SQL text is not a money classifier. Return safe wording and references, not SQL, constraint names, journal payloads or foreign tenant information. No legacy fallback or collect-again instruction on failure; repeated cancellation/notes behavior stays as specified. Future role-specific tests must exercise both guard layers and error precedence as well as RLS-hidden rows.

## 8. Locks, transactions and concurrency obligations

Preserve actual source lock paths; do not invent one global lock order that existing functions do not use:

- Bootstrap: sorted customer email/phone advisory locks → operation advisory lock → new-row insert order.
- Existing persist: operation advisory → original attempt → operation; appointment does not yet exist.
- Existing bind/close/commit and proposed W/X: operation advisory → original attempt → existing appointment → operation. Use the exact existing `booking-operation:` advisory namespace.
- Existing projector: admission shared lock → obligation → attempt → ledger → appointment → aggregate/target/sequence. It does **not** take the operation advisory lock.

**Frozen appointment lock strength (C3):**

| Command | Parent row lock | Reason |
| --- | --- | --- |
| Status, reschedule/resize, staff/Location/service same-basis changes, notes, resource maintenance, other non-key edits | FOR NO KEY UPDATE | Does not alter appointment ID/Business/customer attribution key; compatible with ledger FK key-share checks |
| Customer reassignment | FOR UPDATE | customer_id is part of `appointments_id_business_customer_financial_key`; serialize against FK checks and fresh history verification |
| Cancellation with financial fencing | FOR UPDATE | Preserve accepted strong-lock fence and canonical operation/attempt order |
| Linked DELETE | Refuse in guard | No permitted deletion lock/write protocol |

Ledger insertion's FK validation takes FOR KEY SHARE on the referenced appointment key. FOR UPDATE conflicts with it; FOR NO KEY UPDATE does not. Thus ordinary notes/status edits must not acquire a stronger parent lock just for convenience. Existing financial functions' lock modes are not globally rewritten. Original operation/attempt serialization is retained, so a same-attempt commit can still legitimately wait; the mandatory nonblocking proof uses an independent valid ledger writer or isolated FK insertion, not a claim that every financial path is nonblocking. Prove a held notes/status non-key parent lock does not itself block that independent insertion, and contrast customer/cancel strong-lock contention. [PostgreSQL 17 row locks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

W/X must not acquire obligation/ledger row locks or invoke projectors after holding attempt/appointment. After serializing, use a complete authoritative read for eligibility; do not wait on another payment attempt after locking appointment. Later independent payment writers may have their own attempt before appointment, so “lock all related attempts after the appointment” would add a reverse edge. Customer changes rely on the preserved composite attribution FK and appointment lock as well as the zero-ledger check; a concurrent ledger insert either wins and blocks reassignment, or loses the FK race and fails without reassignment of financial history. Test legacy and durable later-payment writers, not only the original attempt.

At default READ COMMITTED, acquire locks first and perform decision reads afterward; use a new command snapshot after waits. At stronger isolation, serialization failure is a rollback/UNKNOWN transport result needing same-identity recovery, not justification for stale classification. PostgreSQL row/advisory locks and transaction-snapshot semantics support this approach, but do not prove this application's deadlock freedom: [PostgreSQL 17 locking](https://www.postgresql.org/docs/17/explicit-locking.html), [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html).

Auth membership/ownership and destination catalog/assignment reads must be revalidated transactionally, with stable authorization rows locked before K where the future implementation needs revocation serialization. Do not hold those locks while calling network validation. Their authorization/catalogue row modes and sorted multi-Location/resource order must be inventoried against existing administration writers in the SQL implementation review; no new permission promise based on a stale browser session. Admission disables new creates, not authorized recovery/maintenance of already durable appointments.

Operational validation divides into three cases: notes/status do not rerun new-create future-slot/catalog checks; schedule/assignment/service corrections validate the desired current tuple excluding the same appointment; monetary adjustment is refused. Database-side tenant/assignment checks and authoritative slot validation remain mandatory for W; server preflight is helpful but not authoritative. Keep named-staff exclusion protection. Current room/resource/unassigned checks are soft checks; this proposal does not upgrade them to a proven interval reservation lock or enable optional staff. If normal-room concurrency acceptance requires stronger reservation guarantees, record that separate blocker rather than claiming this amendment supplies them.

One lifecycle command, audit, revision, appointment/resource effect and any close fence form one transaction. An exception, failed validation, conflict or audit failure leaves none of that command committed. Earlier committed money is never rolled back by a later lifecycle failure. Use bounded lock/statement timeouts (proposed 5s/30s, subject to local proof); never silently increase. Deadlock/timeout/connection loss preserves identifiers, canonical reread and no blind retry. A network timeout does not prove the server transaction failed.

## 9. Financial, customer and projection compatibility

- Original terminal money is unchanged across every successful lifecycle command. A cancellation is not a refund. Status completed/no_show does not create a charge or erase a deposit. HELD/UNKNOWN never becomes zero.
- No cents/payment-status/amount-paid/refunded field is accepted by W. Existing projection cache updates remain in their existing unguarded-by-lifecycle financial column set; they do not increment operational revision or create an operational journal entry. Avoid an all-columns trigger that would break projectors.
- A request with no payment uses SKIPPED history, not an absent attempt. Financially neutral operational edits require settled original target for scheduling, but do not reopen/re-bootstrap it. Later money must use an intentional separately authorized attempt, never an edit-triggered automatic collection.
- A price/tax/deposit change can invalidate existing invoice/projection truth even with no collected money. Therefore a separate financial-adjustment document/workflow is required: explicit authority, before/after agreement, original preserved quote, invoice/credit/rebill rules, outstanding-balance/refund handling, currency constraints, document identity and concurrency. None exists by assertion in this addendum. Do not use cancel+recreate as a hidden financial transfer workaround. Program Lead must schedule this dependency if launch requires amount-changing edits.
- Service correction under unchanged agreed commercial basis does not rewrite existing invoice lines or receipts. Location move must not silently change the tax jurisdiction/agreement. Incompatibility is a named financial-review hold, not a guessed new catalog price.
- Customer correction checks **all** appointment-linked ledger history, not just original attempt or succeeded rows. Once any exists, refuse customer reassignment; refunds do not erase that history. Original customer/attempt remains traceable after allowed no-ledger correction. Customer merge, transfer of money and delete/cascade are outside scope. Preserve friendly deletion/history-retention behavior and the composite FK.
- Projection failures are separable from appointment maintenance and money settlement. Eligible scheduling/status/notes may proceed while synchronization is incomplete; explicit later convergence is restricted to that operation/attempt and existing admission/watermark. No worker scan or resetting COMPLETE obligations. Canonical reread outranks stale replay PENDING or `recovery_disposition=RECOVER`.
- Cross-editor operational view does not expose the creator's private recovery payload. If the existing creator-only financial reader cannot serve an authorized colleague's maintenance decision, the W server transaction decides the narrow predicate and returns a safe state; it does not impersonate the creator or grant broad private history reads. Full team payment recovery remains outside scope.

## 10. Recovery correction and replacement criterion

Required order for every create retry/resume:

1. Authenticate the current actor and resolve Business; validate only opaque identity syntax/ownership first.
2. Canonically read operation, operation-tagged appointment, attempt/ledger/events and binding under the existing authorized reader. Contradiction/truncation/foreign reference/error returns HOLD/UNKNOWN.
3. If an appointment exists, recover it by original identity; never subject it to new-create availability, future-date or current catalog checks, and never restore its old scheduling tuple. Bind only the same appointment if safely unbound; settled attempt means read, not collect. CLOSED lifecycle cannot be resurrected. A lost result after a later operator edit must return current appointment state and original financial result separately.
4. If an operation exists but no appointment, resume from the protected persisted original request and attempt identity, never browser-reconstructed PII. Before any still-needed insertion, validate current feasibility and fresh authoritative commercial snapshot; changed price/slot fences the old operation using the existing safe close semantics, without silently changing its request. “Only new create” means a genuinely new appointment insertion, not mere response recovery of an existing row.
5. If no operation is visible, ABSENT is only a snapshot result. With the intact original request, same-identity advisory-serialized bootstrap may safely resume; with lost original request, stay UNKNOWN/HOLD. No new key, new customer or collect-again instruction.

Opaque browser storage holds only operation/attempt/inline-customer references partitioned by account/Business context. Server resume loads protected original request/attempt key; ordinary DTO omits notes, customer PII, raw tuples/fingerprints, provider payloads and both raw sequence values. Logout clears local visibility without claiming server cancellation. Preserve #135's synchronous guard across pointer/keyboard/requestSubmit overlaps and ambiguous results; no unconditional error/finally reset.

**Exact safe identity rotation criteria:**

- A new request has positively never been dispatched (local state before network dispatch), and its old identities cannot be reused by another admitted request; or
- Canonical serialized close has committed for the original operation, permanently fencing future create/commit with those identities, with the result reconciled; any saved cancelled appointment/recorded money remains visible; or
- The original operation's result is canonically resolved and the operator deliberately selects **Book Another**, meaning a distinct booking, not retry/replace/repair of the old one. Retain the old result and rotate all three identities together.

An ABSENT read, elapsed time, disabled new admission, aborted browser fetch, two matching empty reads, no recent transactions, or taking/releasing an advisory lock **without a persistent fence** is not a safe replacement criterion: a delayed request could execute later. The current schema provides no absent-operation tombstone. This proposal does not add one or promise automatic recovery when all original references/request are lost. Such cases require governed investigation/HOLD; a later durable absent-key fence would need a separate proof and design gate.
