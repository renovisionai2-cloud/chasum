# Worker reliability hotfix — prepared release contract

This change is based on Production/main `476af17bfd06113281df0b5c33f995ccb26f5fff`. The new migration, `supabase/migrations/20260905024239_communication_send_intents.sql`, is prepared only and must not be applied by running the repository's pending migrations in bulk. Production 029 repair remains pending; the historical queue remains governed by the locked 579-row repair package. This document does not assert a live infrastructure state or authorize any worker invocation.

## Activation and compatibility

`CHASUM_WORKER_RELIABILITY_ENABLED` defaults to false. With that flag off, the background worker must remain held; existing inline booking delivery follows the compatibility path. That compatibility path is not the completed reliability fix and does not authorize processing old queued twins. Deploying with the flag off must not introduce a requirement for the new ledger into current pre-029 inline booking delivery.

With the flag enabled, worker and inline transactional delivery share a durable send-intent reservation before a provider call. Every required database operation must succeed or stop delivery before contacting the provider. A missing table, missing 029 column, permission error, unavailable ledger or unreadable ownership state is a hold/error, not permission to use an unprotected send fallback.

New email, SMS and reminder jobs receive an occurrence UUID. The enqueue path stamps `payload.sendIntentProtocol = "durable-v1"` only while the flag is enabled; it strips a caller-supplied protocol marker while disabled. A UUID alone does not prove that an earlier inline call used the ledger. After activation, the worker holds transactional jobs missing the protocol marker or a valid occurrence UUID for reconciliation, even if they were created by this hotfix while disabled. Do not bulk stamp old payloads or reconstruct accepted ledger rows from incomplete historical logs to bypass this boundary.

The enabled inline booking path also checks legacy queue/sent evidence before attempting an occurrence that lacks authoritative durable evidence. Queue work accumulated while held, including work created between the historical repair and flag activation, needs a separately governed disposition. Deploy and activation must drain already admitted requests and maintain consistent flag state across producers, inline delivery and workers; a rolling mixture of legacy and guarded sends is not a proved safe activation strategy. If reverting the flag after guarded sends begin, keep the relevant inline/resend ingress held as well as the worker until the rollback decision addresses legacy bypass.

The future approved sequence is:

1. Retain verified worker/resend holds and drain already admitted requests.
2. Complete the separately approved, unchanged 029 plus historical-queue repair and its independent SQL/PostgREST verification.
3. Apply only the reviewed new send-intent migration in a separately authorized step, then verify its schema, effective privileges and API visibility while held.
4. Deploy the independently reviewed hotfix with the reliability flag off. Confirm its exact revision and configuration, drain in-flight legacy sends, and review work created since the historical repair. Enable the flag consistently across producers and consumers only after the schema, tests and release approvals are recorded; retained legacy jobs remain held.
5. Perform the separately authorized isolated synthetic worker test on the enabled hotfix. Review new queued work and obtain approval before restoring normal worker ingress/cron.

The ledger itself depends only on `public.businesses(id)`, `gen_random_uuid()` and the standard Supabase roles. It has no dependency on 029, 034–036 or 040/041. Worker execution still requires 029. This hotfix does not apply any migration, neutralize jobs, deploy, enable the flag, or re-enable cron.

The migration uses one explicit transaction, a five-second lock timeout and a 30-second statement timeout. Creation, RLS and privilege changes become visible together. It deliberately fails if the table already exists; do not add `IF NOT EXISTS` to conceal a different schema or increase timeouts without review. The future operator must account for the transaction boundary in the chosen execution method and retain a confirmed COMMIT receipt.

## Send-intent ledger

`public.communication_send_intents` stores one durable record per `(business_id, intent_key)`. The unique constraint resolves concurrent reservation attempts in the database. `intent_key` identifies a logical communication rather than an arbitrary process attempt. Distinct legitimate events and explicitly authorized manual resends need distinct intent identities; a queue retry retains the original identity. Never derive an intent solely from appointment/template when that would suppress a later legitimate message.

The current key hashes the versioned occurrence UUID, channel and template key; the database scopes it by business. The ledger binds that key to the recipient hash, so changing a recipient under the same occurrence is a hold rather than a fresh send. Initial booking and original receipt occurrences are stable in separate namespaces. Reminders use the appointment and canonical scheduled timestamp, so repeating the same scheduling call reuses its occurrence while a different appointment or reminder time remains distinct. Waitlist children use the claimed parent job ID and waitlist entry ID; retrying a partially completed parent reuses each child's identity, while another parent or entry remains distinct. Later booking events and explicit resends receive new UUIDs. A manual queue retry preserves its payload, key and attempts, requires the exact durable protocol and a `rejected` ledger record, and only reactivates an eligible failed job through a checked conditional update. It cannot reset a completed, cancelled, processing, exhausted or uncertain job.

The required identity fields are `id`, `business_id`, `intent_key`, `channel`, `template_key`, `recipient_hash`, `source`, `owner_id` and `attempt`. `owner_id` is an opaque random reservation-owner UUID, not an auth user ID. `first_job_id` and `last_job_id` are nullable correlation UUIDs, deliberately without foreign keys so queue deletion cannot erase or invalidate the acceptance record. They are not authorization evidence. Tenant equality must be enforced by the application when resolving job, appointment and recipient context.

Nullable `entity_type` and `entity_id` correlate an appointment or receipt with its send occurrences. They must be both absent or both present; the type is limited to `appointment` or `receipt` and the ID is a UUID. There is no entity FK, so this addition does not depend on a commerce migration or erase evidence when a domain row is deleted. The application validates that the correlation belongs to the loaded tenant context. Ordinary manual retry must check unresolved delivery for that same entity before creating a new occurrence; it must not impose a blanket hold on another receipt or appointment that happens to share its recipient.

The result fields are `state`, `provider`, `provider_message_id`, `failure_code`, `created_at`, `updated_at` and `accepted_at`. `recipient_hash` is a SHA-256 hex digest; it remains potentially identifying correlation data, not a claim of anonymity. The table contains no raw recipient, payload, message body, provider response or unrestricted error text. `failure_code` accepts only bounded symbolic codes; sanitize provider details into those codes before writing. Intent keys must also be opaque and must not contain recipient addresses. The ledger is operational evidence, not a complete financial audit trail.

| State | Meaning | Automatic retry contract |
|---|---|---|
| `sending` | A process durably reserved the intent before provider contact; acceptance may later be uncertain. | Do not acquire by elapsed time or lease expiry. |
| `accepted` | Provider acceptance is durably recorded. | Suppress duplicate sends; reconcile queue bookkeeping independently. |
| `rejected` | A definitive provider non-acceptance makes another attempt safe. | Guard transition by current state, owner and attempt; increment attempt atomically. |
| `unknown` | Provider acceptance or post-provider persistence is uncertain. | Hold for evidence-based reconciliation; do not automatically resend. |

There is no automatic expiry, cleanup job, state-transition trigger, RPC or job-claim column in this migration. The application checks compare-and-set results using the stored owner and attempt; SQL constraints validate the permitted shape but do not authorize arbitrary state transitions by a privileged service client. A queue finalization error must not turn an accepted/unknown intent into retry permission. `updated_at` is updated explicitly by application transitions; its default does not constitute an automatic trigger.

Job ownership uses an atomic conditional UPDATE against existing queue columns, including pending status, tenant, cancellation state, scheduled/retry eligibility, attempts and the observed maximum. Only a returned claimed row permits execution. A random claim token, attempt and start timestamp fence completion/retry writes. Processing jobs are never automatically stolen after a timeout; a stranded owner requires review. A provider acceptance followed by failed intent persistence leaves the pre-send `sending` reservation intact, returns accepted delivery with reconciliation required to the current caller, and prevents a later automatic call. A failed log, audit, timeline or queue write also preserves provider acceptance.

The durable replay unit covers each email, SMS or reminder occurrence, including waitlist child emails. Calendar sync, webhook, recurring and waitlist parent jobs retain their baseline bounded retry behavior; this patch does not establish idempotency for all their side effects. A repeated scheduling call can still insert duplicate reminder job rows, and a partially completed waitlist parent can enqueue duplicate child rows, but their shared stable occurrences prevent independent provider sends. Direct waitlist calls without a parent job ID represent new occurrences. Waitlist status and in-app bookkeeping are checked but not one atomic transaction; an in-app notification can remain absent if a status write succeeds and the subsequent notification insert fails. Do not claim that this hotfix gives every background job exactly-once effects.

Resend accepts an `Idempotency-Key` header on email requests but retains its keys for only 24 hours. That provider window is a second layer, not the retention or expiry policy for this ledger. Keep accepted/unknown/sending evidence beyond the provider window and never infer that an unknown send becomes safe to retry after 24 hours. A definite rejection followed by an approved retry still uses a well-defined logical intent and must respect the provider's payload/key contract. [Resend idempotency documentation](https://resend.com/docs/dashboard/emails/idempotency-keys).

## Access and tenant boundary

RLS is enabled and forced on the new table. There are no tenant-owner, anonymous or authenticated policies. Explicit grants are cleared for PUBLIC, anon, authenticated and service_role; only SELECT, INSERT and UPDATE are granted back to service_role. DELETE, TRUNCATE, TRIGGER and REFERENCES are not intentionally granted. Existing table policies are unchanged.

The standard Supabase service role bypasses RLS, so application tenant predicates are required on every lookup/transition. Forced RLS does not restrict superusers or BYPASSRLS roles. The business-scoped unique key permits the same opaque intent key for different businesses, but does not itself validate a caller's business authorization. The parent business FK cascades when an authorized business deletion occurs; this ledger is durable for normal delivery retries, not immutable against privileged writes or tenant deletion. Future tenant deletion/retention work must consider that evidence loss.

PostgreSQL documents the [default-deny behavior of RLS and BYPASSRLS exceptions](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) and the [database uniqueness and FK semantics](https://www.postgresql.org/docs/17/ddl-constraints.html) used here.

## Forward recovery and rollback

If activation fails, retain worker holds and investigate with the ledger intact. Do not drop/truncate the ledger or delete accepted/unknown rows while any send could recur. Do not reset sending/unknown intents or historical terminal queue rows for convenience. Roll back application deployment only while workers and relevant send ingress remain held; reverting to a legacy inline path can bypass this ledger, so its send behavior requires an explicit governed decision.

Turning the flag off is a worker hold, not permission for automatic resend or a complete delivery rollback. An already accepted provider action cannot be rolled back by changing a database row. Prefer a reviewed forward fix and provider-evidence reconciliation. Dropping the unused ledger could only be considered under a separate decision proving no sends were attempted and no durable evidence must be retained; no destructive rollback script is supplied.
